# 元哥的飞书研发助手：开发过程记录

> 一个“群消息 → 任务 → 分析 → 批准 → 开发”的机器人，跑在 OpenCode 上。
> 本文只讲做了什么、为什么这么做、踩过什么坑，适合内部分享。

---

## 1. 它解决什么问题

研发人员每天在飞书群里被三类消息淹没：

1. 直接 @我 的消息；
2. 直接 @机器人 的消息；
3. **没 @ 我、但和我职责/项目相关**的消息。

前两类可以实时处理，第三类最容易被漏掉。全量丢给大模型又太贵、太慢。

所以目标很明确：

- @我 / @机器人：秒级响应；
- 非 @ 消息：定时拉取、低成本筛选、只推送相关的；
- 需要我决策的：群里 @ 我，或者私聊请示；
- 批准后才允许改代码；
- 全程留痕，能回溯。

---

## 2. 整体架构

```text
飞书（长连接 + 历史消息接口）
        │
        ▼
守护进程（确定性逻辑，不烧 token）
  ├─ 去重 / 游标 / 限流 / 并发调度
  ├─ 关键词初筛 + 必要性判断
  └─ 分派
       ├─ 快路径：群回复 / @我 / 私聊通知
       └─ 慢路径：OpenCode 子会话（分析 / 执行 / 评审）
```

核心原则：**确定性的活交给代码，需要判断的活才交给模型。**

## 3. 几个关键设计决策

### 3.1 为什么不用“一个会话包打天下”

一条 @ 消息不要新建一个长期会话，否则会话数量会无限增长。

最终方案：

| 用途 | 会话 | 生命周期 |
|------|------|----------|
| 群锚点 | 每群一个 coordinator | 长期 |
| 分析 / 执行 / 评审 | 每任务一个 child | 7 天归档 / 30 天删 |
| 群回复 / 批量筛选 | 临时 child | 用完即删 |

coordinator 只做锚点，不跑 prompt，避免 `SessionBusyError`，同群还能并发。

### 3.2 为什么“拉历史”不是子代理

子代理是一次性深度任务，干完就结束，不能常驻轮询。
拉历史是确定性代码：分页、游标、去重、限流，全部自己控制。

### 3.3 为什么回复要“简洁优先”

默认不超过 320 字，只给结论和下一步。
只有对方明确说“详细/步骤/why/how”，才展开到 2000 字。

群聊里没人想看一篇长文。

### 3.4 为什么需要“必要性判断”

@机器人 ≠ 必须回复。先判断：

- `answer`：直接答；
- `need_decision`：涉及排期、承诺、上线、风险，群里 @ 我；
- `notify_owner`：只需知会，私聊我；
- `no_reply`：寒暄、感谢，保持安静。

低置信度不硬答，默认升级。

### 3.5 为什么按人限流

一个同事连续刷屏，不能把机器人打爆。

- 每人每分钟 6 条
- 每人并发 1
- 冷却 5 秒
- 超限只警告一次，后续静默丢弃

不同同事之间仍然并发处理。

## 4. 踩过的坑

### 坑 1：消息拉到但没处理

配置关了筛选，代码第一行直接 `return`，消息被静默丢弃，游标却前进了。
修复：筛选关闭时改为原样摘要转发，绝不静默丢。

### 坑 2：历史消息接口一直 400

不是网络问题，是权限缺失。
飞书要求 `im:message:readonly`（后台不一定叫“历史消息”）。
现在 `doctor` 会直接探测并提示缺哪个 scope。

### 坑 3：群名显示成“群 1”

setup 里为了占位编了个名字，导致日志不可读。
修复：目录和日志改用真实群名 + `chatId`，群名通过接口查询并缓存。

### 坑 4：审批按钮点完不变灰

卡片回调只返回 toast，没有更新卡片。
修复：回调返回新卡片，按钮置灰、标题显示“已处理”。

### 坑 5：表格在截图里，模型看不到

同事发的是“一句话 + 一张截图 + 两条 SQL 注释”。
旧实现只取文字、丢掉图片，模型自然来问表名。
修复：图片保留占位，后续接视觉解析；短时间内的同人连续消息做聚合。

### 坑 6：会话无限增长

筛选每 3 分钟一次，每次都新建会话且不删除。
修复：筛选会话用完即删；任务结束归档 child；7/30 天清理。

### 坑 7：WSL2 内存被打满

反复安装、多个 OpenCode 各拉起一套 MCP，内存吃紧。
经验：少开 TUI、多用 attach、别在源码目录反复构建。

## 5. 现在的效果

- @机器人：秒级回复，简洁优先；
- @我：默认私聊请示，批准后引用回复并标注“（助手代答）”；
- 非 @ 相关消息：定时汇总，附判断理由和原消息摘要；
- 需要决策：群里 @ 我，附问题、来源、原因；
- 未批准：代码零改动；
- 重启：补拉、去重、未完成任务续作；
- 全程：结构化日志 + 审计。

---

## 6. 我学到的

1. **先把“确定性”和“智能”分开**：能写代码判断的，不要交给模型。
2. **默认最小副作用**：不自动回复、不自动合并、不自动执行。
3. **失败要可见**：静默丢弃是最危险的 bug。
4. **上下文要分层**：实时短聚合、历史关联、长期记忆，不能混成一锅。
5. **先做最小验证**：飞书权限、事件、卡片回调，必须先用脚本跑通。

## 8. 一句话总结

**让机器人做“分诊 + 分析 + 留痕”，把“决策”和“改代码”的最终权限留给人。**
