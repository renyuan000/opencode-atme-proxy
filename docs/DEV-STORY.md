# 元哥的飞书研发助手：开发过程记录

> 一个“群消息 → 任务 → 分析 → 批准 → 开发”的机器人，跑在 OpenCode 上。
> 本文只讲做了什么、为什么这么做、踩过什么坑，适合内部分享。

---

## 0. 架构总览

```text
                        飞书 / 群聊
             @我        @机器人        非 @ 消息
              │            │              │
       实时事件(长连接) ────┤              │ 周期拉取(历史消息)
                           ▼              ▼
        ┌──────────────────────────────────────────┐
        │ 守护进程（确定性逻辑，不烧 token）          │
        │ 去重 → 限流 → 短聚合 → 关键词/必要性判断    │
        └──────────┬───────────────────┬───────────┘
                   │ 快路径             │ 慢路径
                   ▼                   ▼
        ┌────────────────────┐  ┌─────────────────────────┐
        │ 群回复 / @我请示    │  │ coordinator(每群1个锚点) │
        │ 私聊通知 / 审批卡   │  │  ├─ analyst  只读分析    │
        └────────────────────┘  │  ├─ executor 批准后执行  │
                                │  └─ reviewer 只读评审    │
                                └────────────┬────────────┘
                                             ▼
                                ┌─────────────────────────┐
                                │ OpenCode（模型+工具+仓库）│
                                └────────────┬────────────┘
                                             ▼
                                ┌─────────────────────────┐
                                │ 回写 + 审计 + 记忆 + 证据 │
                                └─────────────────────────┘
```

一句话：**代码负责「收、筛、分、记」，模型负责「理解、分析、执行」，人负责「批准」。**

---

## 1. 它解决什么问题

研发人员每天在飞书群里被三类消息淹没：

1. 直接 @我 的消息；
2. 直接 @机器人 的消息；
3. **没 @ 我、但和我职责/项目相关**的消息。

前两类可以实时处理，第三类最容易被漏掉。全量丢给大模型又太贵、太慢。

所以目标很明确：

- @我 / @机器人：秒级响应；
- 非 @ 消息：定时拉取、按配置筛选（默认复用 OpenCode 模型）、只推送相关的；
- 需要我决策的：群里 @ 我，或者私聊请示；
- 批准后才允许改代码；
- 全程留痕，能回溯。

## 2. 一条消息的旅程

以“同事在群里 @我，随后补充两条表结构说明”为例：

```text
17:42:17  同事 @我 + 截图
              │
              ▼
        去重 → 是否白名单群 → 是否 @我
              │
              ▼
        等 5 秒收集同人连续消息
              │
              ▼
        LLM 判断：后面两条是不是同一件事
              │
       ┌──────┴───────┐
       │ 是            │ 不是
       ▼               ▼
   合并为一条逻辑消息   分开处理
       │
       ▼
  相关性与任务识别（是否我的任务）
       │
       ▼
  任务分析（目标/范围/风险/验收）
       │
       ▼
  私聊审批卡（计划 + 计划哈希）
       │
       ▼
  批准 → 开发执行 → 测试 → 评审 → 回写
```

关键点：**5 秒只是“连续发送”的聚合；隔几十秒的补充，靠历史关联挂回原任务。**

## 3. 几个关键设计决策

### 3.1 为什么不用“一个会话包打天下”

一条 @ 消息不要新建一个长期会话，否则会话数量会无限增长。

最终方案：

| 用途              | 会话                 | 生命周期           |
|-------------------|----------------------|--------------------|
| 群锚点            | 每群一个 coordinator | 长期               |
| 群摘要            | 每群一个持久会话     | 长期               |
| 分析 / 评审       | 每群持久 worker      | 长期               |
| 执行              | 每任务一个 child     | 7 天归档 / 30 天删 |
| 群回复 / 批量筛选 | 临时 child           | 用完即删           |

> 以上是当前实现 v0.2；v1.3 目标（主 session / 群会话 / 角色 worker）见 `docs/SESSION-ARCHITECTURE-REVIEW.md` 第 12 节。

coordinator 只做锚点，不跑 prompt，避免 `SessionBusyError`，同群还能并发。

### 3.2 为什么“拉历史”不是子代理

子代理是一次性深度任务，干完就结束，不能常驻轮询。
拉历史是确定性代码：分页、游标、去重、限流，全部自己控制。

### 3.3 为什么回复要“简洁优先”

默认不超过 320 字，只给结论和下一步。
只有对方明确说“详细/步骤/why/how”，才展开到 2000 字。

群聊里没人想看一篇长文。

### 3.4 为什么需要“必要性判断”

@机器人 ≠ 必须回复。先判断：

- `answer`：直接答；
- `need_decision`：涉及排期、承诺、上线、风险，群里 @ 我；
- `notify_owner`：只需知会，私聊我；
- `no_reply`：寒暄、感谢，保持安静。

低置信度不硬答，默认升级。

### 3.5 为什么按人限流

一个同事连续刷屏，不能把机器人打爆。

- 每人每分钟 6 条
- 每人并发 1
- 冷却 5 秒
- 超限只警告一次，后续静默丢弃

不同同事之间仍然并发处理。

## 4. 踩过的坑

### 坑 1：消息拉到但没处理

配置关了筛选，代码第一行直接 `return`，消息被静默丢弃，游标却前进了。
修复：筛选关闭时改为原样摘要转发，绝不静默丢。

### 坑 2：历史消息接口一直 400

不是网络问题，是权限缺失。
飞书要求 `im:message:readonly`（后台不一定叫“历史消息”）。
现在 `doctor` 会直接探测并提示缺哪个 scope。

### 坑 3：群名显示成“群 1”

setup 里为了占位编了个名字，导致日志不可读。
修复：目录和日志改用真实群名 + `chatId`，群名通过接口查询并缓存。

### 坑 4：审批按钮点完不变灰

卡片回调只返回 toast，没有更新卡片。
修复：回调返回新卡片，按钮置灰、标题显示“已处理”。

### 坑 5：表格在截图里，模型看不到

同事发的是“一句话 + 一张截图 + 两条 SQL 注释”。
旧实现只取文字、丢掉图片，模型自然来问表名。
修复：图片保留占位，后续接视觉解析；短时间内的同人连续消息做聚合。

### 坑 6：会话无限增长

筛选每 3 分钟一次，每次都新建会话且不删除。
修复：筛选会话用完即删；任务结束归档 child；7/30 天清理。

### 坑 7：WSL2 内存被打满

反复安装、多个 OpenCode 各拉起一套 MCP，内存吃紧。
经验：少开 TUI、多用 attach、别在源码目录反复构建。

### 坑 8：审批卡片的“处理中”体验

回调只返回 toast，用户点完看不到状态，也不知道是否成功。
修复：回调返回新卡片，按钮置灰、标题显示“已处理”，并附处理结果。

### 坑 9：日志时间看不懂

日志用 UTC，本地看差 8 小时，排查时容易误判。
修复：日志和消息摘要统一使用本地时间，带 `+08:00` 偏移。

## 5. 现在的效果

- @机器人：秒级回复，简洁优先；
- @我：默认私聊请示，批准后引用回复并标注“（助手代答）”；
- 非 @ 相关消息：定时汇总，附判断理由和原消息摘要；
- 需要决策：群里 @ 我，附问题、来源、原因；
- 未批准：代码零改动；
- 重启：补拉、去重、未完成任务续作；
- 全程：结构化日志 + 审计。

---

## 6. 我学到的

1. **先把“确定性”和“智能”分开**：能写代码判断的，不要交给模型。
2. **默认最小副作用**：不自动回复、不自动合并、不自动执行。
3. **失败要可见**：静默丢弃是最危险的 bug。
4. **上下文要分层**：事件单元聚合、按需回溯、长期记忆，不能混成一锅。
5. **先做最小验证**：飞书权限、事件、卡片回调，必须先用脚本跑通。
