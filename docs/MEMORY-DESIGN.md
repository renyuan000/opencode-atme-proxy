# 记忆与证据设计

| 项目 | 内容                                                         |
|------|--------------------------------------------------------------|
| 版本 | v1.3（已确认）                                                 |
| 日期 | 2026-11-17                                                   |
| 状态 | v1.3 设计定稿；先评审再编码                                   |
| 关联 | `docs/REQUIREMENTS.md`、`docs/SESSION-ARCHITECTURE-REVIEW.md` |

> 目标：与我和我的项目高度相关的群消息、回复，长期留存并可随时召回；低相关消息不长期占用空间；记忆提炼必须经过评审，重要结论要由我确认；新消息能与历史聊天、记忆、任务做关联，而不是只看当前一句。

---

## 1. 结论

- **证据按群 + 日期存 720 天**，保留原文和 `message_id`。
- **记忆只留高价值结论**：决策、截止、任务、事实、偏好、结论。
- **高影响记忆必须我确认后才置顶**：决策 / 截止。
- **提炼与评审分两步**，避免模型自证。
- **新消息要做历史关联**：先判事件单元是否完整；不完整才回溯，硬上限 50 条 / 7 天，结合记忆与未关闭任务。
- **临时 child session 不是长期记忆**，7 天归档 / 30 天删除；主 session、群会话、角色 worker 为持久会话，不参与该清理。
- **上下文以事件单元为单位组装**：完整则独立处理，不完整才按需回溯。
- **群会话是唯一群事实源**；角色 worker 持久，任务上下文按 job 隔离。
- 不做五层目录、不做复杂信任模型、不做大批指标；保持最小可用。

## 2. 为什么不能依赖 OpenCode session

事实（本机实测）：

- `opencode.db` 约 1.1 GB，67 个 session、2.1 万条 message、8 万条 part。
- session 删除会永久移除消息和历史。
- 归档只是 `time_archived` 标记，不是长期归档策略。
- session 会被 compact，细节有损。
- session 没有按群/日期的检索结构。

因此：

| 层                     | 作用                | 是否长期       |
|------------------------|---------------------|----------------|
| 临时 child session     | 对话载体、调试       | 否，7/30 天清理 |
| 持久会话（主/群/worker） | 上下文与调度        | 是，长期        |
| 证据文件               | 召回、审计、复盘      | 是，720 天      |
| 记忆文件               | 跨会话召回          | 是，pinned 永久 |
| 任务档案               | 分析/审批/执行/评审 | 是             |

`compacting` 只是 session 内的滚动窗口，不能替代长期记忆。正确关系：

```text
长期记忆（文件）→ 注入上下文 → session 对话 → compacting 滚动
```

## 3. 三层上下文模型

这是本设计的核心：**不要把所有历史塞进 prompt，而是按当前消息重建一个小上下文。**

```text
A. 事件单元（实时聚合）
   同群同人、就近时间的连续消息，向前回溯 + 向后收集
   ≤5 秒直接合并；5~60 秒由 LLM 判断是否同一件事；有引用则优先合并
   合并为一条“逻辑消息”，保留全部 messageId

B. 历史聊天关联（按需）
   不完整的事件单元，按引用 → 同人近邻 → 同话题（7 天）回溯
   加上 pinned 记忆和未关闭任务
   用 LLM 判断当前消息与谁相关

C. 长期记忆
   提炼后的决策、截止、承诺、事实、结论
   按群/日期存，pinned 永久
```

三层的关系：

| 层         | 输入                   | 输出         | 上限                       |
|------------|------------------------|--------------|----------------------------|
| A 事件单元 | 原始消息流             | 一条逻辑消息 | 5 条 / 4000 字             |
| B 历史关联 | 逻辑消息 + 记忆 + 任务 | 关联决策     | 按需 / 硬上限 50 条 / 7 天 |
| C 长期记忆 | 相关证据               | 可召回结论   | 每群数百条                 |

A 解决“同一句话被拆成几条发”，B 解决“隔很久补充同一件事”，C 解决“跨周跨月还能想起来”。

组装原则：先判断事件单元是否完整独立。完整则独立处理，只带 pinned 记忆与相关任务摘要；不完整才按“引用 → 同人近邻 → 同话题 → 记忆”回溯，补齐“谁 / 对什么 / 做什么 / 约束 / 何时”即停。50 条 / 6000 字只是硬上限，不是选取目标。

## 4. 目录结构

```text
<stateDir>/
  memory/
    <chatId>/                    按群分片（当前实现）
      records.json              当前有效记忆，按 id 去重（长期）
      history/
        2026-11-16.jsonl        记忆变更历史（720 天）
    index.json                  群与记录数索引
  replies/
    <群名__chatId>/
      2026-11-16.jsonl          相关原文与回复（720 天）
  tasks/
    <taskId>.json
  analyses/<taskId>/<version>.json
  approvals/<taskId>.json
  executions/<taskId>.json
  reviews/<taskId>.json
  chat-context.json             群会话事件单元索引 / 7 天，只给 prompt
  dedup.json                    低相关消息只留 message_id
  audit.jsonl                   只记动作与 ID，不记正文
```

目录命名：

- 记忆当前用 `<chatId>` 分片；目标命名 `群名__chatId`，群名从 `index.json` 补。
- 证据用 `群名__chatId`；群名去掉 `/ \ : * ? " < > |`，截断 40 字符。
- 群名为空或未解析时用 `群__<chatId>`。
- 群名变更不改目录名，`index.json` 记录最新 `chatName`。

规则：

- 按群分目录，按日期分文件，避免单文件膨胀。
- 回溯时按日期直接定位，不扫全量。
- 权限 600/700。
- 删除按群 / 任务 / 日期，按文件操作。

## 5. 数据模型

### 5.1 证据记录（replies）

```json
{
  "chatId": "oc_...",
  "chatName": "产品-流分装置",
  "date": "2026-11-16",
  "direction": "inbound | outbound",
  "messageId": "om_in_...",
  "replyMessageId": "om_out_...",
  "kind": "bot_mention | proxy_reply | direct | owner_notify | review",
  "text": "回复原文",
  "model": "opencode",
  "reason": "必要性判断理由",
  "taskId": "task_...",
  "createdAt": 1794800000000
}
```

- 只记录与“我/项目高度相关”的消息与回复；`direction` 区分入站原文与机器人回复。
- 低相关消息不写正文，只在 `dedup.json` 留 `message_id`。
- 默认存摘要 + `messageId`；全文需显式开启，避免长期保存敏感内容。
- 保留 720 天。

### 5.2 当前有效记忆（records.json）

```json
{
  "version": 1,
  "chats": {
    "oc_...": {
      "chatName": "产品-流分装置",
      "updatedAt": 1794800000000,
      "records": {
        "deadline:资产台账拆表": {
          "kind": "deadline",
          "key": "资产台账拆表-截止",
          "value": "11-20 前完成",
          "sourceMessageIds": ["om_..."],
          "pinned": true,
          "createdAt": 1794800000000,
          "updatedAt": 1794800000000
        }
      }
    }
  }
}
```

强制规则：

- `sourceMessageIds` 至少 1 条，否则拒收。
- `kind` 只允许 `task | decision | fact | preference | deadline | outcome`。
- 同一 `chatId + kind + key` 视为同一条；新值覆盖旧值，旧值写入 `history/`。
- `task / decision / deadline` 默认 `pinned`；其中 `decision / deadline` 必须经我确认。
- `fact / outcome` 可自动入库，默认不 pin。

规模预期：

```text
每群活跃记忆 100–500 条
5 群约 2500 条，单条约 150 字节 → 约 375 KB
同 key 只保留最新，不随 720 天线性膨胀
```

### 5.3 记忆变更史（history）

```json
{
  "ts": 1794800000000,
  "action": "upsert | supersede | pin | unpin | delete",
  "key": "资产台账拆表-截止",
  "before": "11-25 前完成",
  "after": "11-20 前完成",
  "sourceMessageIds": ["om_..."],
  "actor": "curator | reviewer | owner"
}
```

- 只追加，不修改。
- 用于回溯和重建记忆。
- 保留 720 天。

### 5.4 群索引（index.json）

只放：

- 该群 pinned 记录（引用，不复制正文）
- 最近一次提炼时间与水位
- 项目绑定信息
- 文件清单

不放大段正文，避免索引膨胀。

## 6. 事件单元聚合（v1.3 目标；当前已实现基本窗口）

触发：@我 或 @机器人 的消息；普通相关消息也会持续 ingest 到群会话，只是不触发回复。

规则：

1. 同群、同发送人；向前回溯到本 burst 起点，向后收集到静默。
2. 间隔 ≤ 5 秒：直接合并，不调用模型。
3. 间隔 5~60 秒：候选，由 LLM 判断是否同一件事，是才合并。
4. 间隔 > 60 秒：默认不合并；有 reply / quote / thread 引用时例外。
5. 中间有他人发言：视为新话题，停止向后合并。
6. 最多 5 条，总字符 ≤ 4000；超出则新起一个事件单元。
7. 合并后保留全部 `messageId`，作为事件单元来源。
8. LLM 判断失败时保守合并，不丢信息，并记日志。

配置：

```json
{
  "context": {
    "burstGrouping": true,
    "burstWaitMs": 5000,
    "burstWindowSeconds": 5,
    "burstMaxMessages": 5,
    "burstMaxChars": 4000,
    "storeMediaPlaceholders": true
  }
}
```

媒体与超长消息：

- 图片 / 文件 / 视频 / 音频统一存占位符（`[图片，未解析]`、`[文件 name，未解析]` 等）；非 @ 也保存，`context.storeMediaPlaceholders` 可关闭。
- 超过 `maxCharsPerMessage` 时保留头 70% + 尾 30%，中间标 `…[截断]…`，按码点截断，避免丢结论和附件标记。

局限：时间只是启发式。超过 60 秒且无引用的补充，交给第 7 节历史关联；有 reply / quote 引用时不受时间限制。

## 7. 历史聊天关联（新增）

### 7.1 目标

新消息进来时，不只看当前一句，而是结合：

```text
A. 按需回溯的事件单元（硬上限 50 条 / 7 天）
B. 该群 pinned 记忆 + 关键词命中的历史记忆（Top 8）
C. 同群未关闭任务（7 天内，最多 5 个）
```

判断它属于：

- 已有话题的延续
- 已有任务的补充
- 与某条记忆相关的新事实
- 全新事项

### 7.2 输入构建

- 事件单元：第 6 节聚合后的结果；未聚合的按原消息。
- 完整性判断：对象、动作、约束、时间、指代是否齐全；完整则不再回溯。
- 不完整时按序回溯：reply / quote 原消息 → 同人同群近邻 → 同群同话题（7 天内）→ 记忆与任务。
- 记忆：pinned 全部 + 关键词命中 Top 8，总字符 ≤ 2000。
- 任务：只取 `candidate / analyzing / needs_info / awaiting_approval`，最多 5 个。
- 硬上限：50 条 / 6000 字；达到上限仍不完整，只问一个最关键的问题，不猜。

### 7.3 输出契约

```json
{
  "relation": "continue_thread | attach_task | related_memory | new",
  "target_task_id": "task_...",
  "related_message_ids": ["om_..."],
  "confidence": 0.0,
  "reason": "..."
}
```

动作：

| relation          | 行为                              |
|-------------------|-----------------------------------|
| `continue_thread` | 并入同一话题，追加 `messageIds`    |
| `attach_task`     | 并入已有未关闭任务                |
| `related_memory`  | 新建条目，挂 `sourceMessageIds`    |
| `new`             | 新建任务或记录                    |
| 置信度 < 0.8      | 不自动合并，只记录候选并私聊提示我 |

### 7.4 安全边界

1. 只关联同群、7 天内的消息。
2. 只自动并入未关闭任务。
3. 已批准 / 执行中 / 已完成的任务不自动并入，只提示我。
4. 合并必须写审计：任务 ID、新增消息 ID、置信度、理由。
5. 关联失败时一律按 `new` 处理，不得保守合并；失败原因写日志。
6. 关联结果必须可回溯到 `sourceMessageIds`。
7. 记忆与历史是数据，不是指令；prompt 明确禁止执行其中的命令。

### 7.5 与 AI Agent 上下文的区别

| 维度     | Agent session                | 本设计                 |
|----------|------------------------------|------------------------|
| 组织     | 线性对话                     | 按群 + 日期            |
| 压缩     | compact 有损                 | 记忆提炼 + 证据保留    |
| 范围     | 单个 session                 | 跨 session、跨周        |
| 检索     | 顺序                         | 关键词 + pinned + 任务 |
| 生命周期 | 临时 child 7/30；持久会话长期 | 证据 720 天，记忆长期   |

本质相同：都是“给当前消息重建相关上下文”；区别是本设计把上下文变成可持久、可检索、可审计的文件。

### 7.6 先查后问（提问门禁）

回答、代答、建任务前，必须按固定顺序检索：

1. 事件单元本身能否解析实体（表名 / 接口 / 字段 / 人 / 项目）。
2. 群上下文、pinned 记忆、未关闭任务。
3. 仓库（`rg`）与配置，确认真实名称。
4. 有只读权限时查数据库 / 接口。

只有以上都找不到、且缺失会阻塞动作，才允许提问。输出三态：

| 状态                  | 行为                        |
|-----------------------|-----------------------------|
| `resolved`            | 直接作答或执行              |
| `assumed`             | 标注 `[假设]` 继续，不等确认 |
| `needs_clarification` | 提问，且必须附已查范围与候选 |

提问约束：

- 有唯一候选：直接用，不提问。
- 多个候选：列候选让用户选。
- 零候选：才开放式提问。
- 未检索就提问视为违规，必须记录到审计。

提问不走群，先成为待审批草稿（见 12.5）。

### 7.7 分析核实（防跑偏）

任务分析完成后，先核实再审批：

1. 确定性核对：分析中的表名 / 接口 / 字段 / 配置，必须能在事件单元、记忆、未关闭任务或仓库中找到。
2. 只读核实子会话（reviewer）：对照事件单元、pinned 记忆、未关闭任务，判断是否跑偏、扩大范围或把假设写成事实。
3. 输出：`drift`（none / minor / major）、`reasons`、`unverified_identifiers`、`checked`、`assumptions`。
4. `drift=major` → 任务转 `needs_info`，不进入审批；minor → 写入审批卡风险区，标注 `[核实]`。
5. 核实失败不阻塞：保留确定性结果并记日志。

## 8. 入库流程

```text
每天一次，每群：
  1. 取昨日相关消息 + 回复 + 任务结论
  2. 一次 LLM 调用：产出候选记忆 JSON
  3. 一次评审调用：逐条核对 sourceMessageIds 与原文
  4. fact / outcome 且评审通过 → 直接入库
  5. task / decision / deadline → 默认 pin；decision / deadline 需私聊我确认
  6. 评审不通过 → 不写入记忆，原文仍保留
  7. 失败不删原文，次日重试
```

约束：

- 提炼与评审是两个独立调用，不能同一轮自我确认。
- 两者都只读，禁止修改文件、执行命令。
- 单群单日设 token 预算上限。
- 评审必须引用 `sourceMessageIds`，无来源直接驳回。

## 9. 召回流程

回答、任务分析、评审时按顺序取：

1. 该群 pinned 的决策 / 截止 / 承诺
2. 该群最近 7 天记忆
3. 关键词命中的历史记忆
4. 相关任务的结论（`outcome`）
5. 历史关联命中的逻辑消息（第 7 节）

限制：

- 条数默认 8，字符上限 2000，可配。
- 冲突时以当前消息为准，记忆只作参考。
- 未确认的决策不进 prompt 的“已确认”区，避免误导。

`chat-context.json` 保存群会话的事件单元索引（硬上限 50 条 / 7 天），用于连续对话与历史关联；它不是长期记忆库。

## 10. 保留与清理

| 数据                   | 保留                         | 说明                                         |
|------------------------|------------------------------|----------------------------------------------|
| 临时 child session     | 7 天归档 / 30 天删除         | 只清理对话载体；持久会话豁免                  |
| 持久会话（主/群/worker） | 长期                         | 不参与 7/30 清理                             |
| 相关原文与回复         | 720 天                       | `replies/<群名__chatId>/<date>.jsonl`        |
| 低相关消息             | 不存正文                     | 只留 `message_id`                            |
| 当前记忆               | pinned 永久；非 pinned 720 天 | `memory/<群名__chatId>/records.json`         |
| 记忆变更史             | 720 天                       | `memory/<群名__chatId>/history/<date>.jsonl` |
| 任务档案               | 长期                         | 体积小，review 必需                           |
| 热点上下文             | 7 天 / 50 条                 | 只给 prompt                                  |
| 审计                   | 1 年                         | 只记动作与 ID                                |

**关键澄清**：7/30 天只清理临时 child session，不清理持久会话、证据和记忆。记忆能否召回，取决于是否被提炼进文件，与 session 是否还在无关。

## 11. 与群历史的关系

我能在群里看到聊天历史，但机器人不能依赖它：

- 群历史不含机器人的判断理由和历史结论。
- 消息可能被撤回、删除。
- 飞书历史无法按任务、按记忆检索。
- 历史接口受权限与分页限制。

所以机器人必须自己保存：

- 高相关原文证据（720 天）
- 结构化记忆（pinned 永久）
- 任务档案（长期）
- 历史关联所需的事件单元索引（硬上限 50 条 / 7 天）

## 12. 会话设计（v1.3）

三层会话，职责固定：

| 会话            | 数量   | 持久     | 职责                                      | 清理 |
|-----------------|--------|----------|-------------------------------------------|------|
| 全局主 session  | 1      | 是       | 插件管理、owner 私聊、审批、跨群汇总         | 长期 |
| 群会话          | 每群 1 | 是       | 唯一群事实源：聚合、组装、摘要、记忆整理、调度 | 长期 |
| 扫描器          | 1      | 状态持久 | 周期拉历史、去重、游标；默认不跑 LLM         | 长期 |
| reply worker    | 角色池 | 是       | 代答草稿（fork 群会话快照）                 | 长期 |
| analyst worker  | 角色池 | 是       | 任务分析（fork）                            | 长期 |
| executor worker | 角色池 | 是       | 改代码（isolated + 独立 worktree）          | 长期 |
| reviewer worker | 角色池 | 是       | 只读复核（isolated）                        | 长期 |

规则：

- 持久的是**角色岗位**，不是单次任务；每个 job 结束即清任务上下文。
- 群会话只做聚合、组装、调度，不跑长任务、不执行代码。
- 扫描器是确定性代码 + 游标，只有拿不准的消息才升级给 LLM 过滤。
- 现有配置 `maxChildrenPerTask` / `maxChildrenGlobal` 语义上对应 `maxJobsPerTask` / `maxWorkersGlobal`，v1.3 不新增键；`depth=1`；超出排队，不拒绝。

当前实现：群摘要会话独立持久（`group:<platform>:<chatId>`），每 `summaryEveryMessages` 条更新一次，单写者串行；摘要注入 reply 与 analysis。角色 worker 仍是每任务临时 child。

### 12.1 上下文所有权（防串味）

| 上下文       | 归属        | 生命周期 | 内容                               |
|--------------|-------------|----------|------------------------------------|
| 群事实       | 群会话独占  | 长期     | 群消息、决策、任务、摘要              |
| 角色工作记忆 | 每个 worker | 长期     | 规范、工具偏好、历史产出索引         |
| 任务上下文   | 每个 job    | 短期     | 群会话推来的事件单元 + 引用 + 约束 |

- worker 不得自建群记忆；群事实只认群会话。
- 角色记忆只存经验与索引，不存他人任务细节。
- job 结束清空任务上下文；需要时重新推送。

### 12.2 上下文信封（群会话 → worker）

```json
{
  "jobId": "job_...",
  "origin": { "chatId": "oc_...", "eventIds": ["om_..."], "senderId": "ou_..." },
  "event": { "text": "...", "at": 0 },
  "references": [{ "messageId": "om_...", "reason": "reply" }],
  "pinned": ["..."],
  "openTasks": [{ "taskId": "task_...", "title": "..." }],
  "contextSufficiency": { "known": [], "unknown": [], "candidates": [] },
  "role": "analyst | executor | reviewer | reply",
  "mode": "fork | isolated",
  "outputSchema": "analysis | execution | review | reply | question",
  "idempotencyKey": "chatId:eventIds"
}
```

- 信封只读；worker 的产出回给群会话，由群会话决定是否落库或发送。
- `idempotencyKey` 保证重复投递只执行一次。

### 12.3 并发与顺序

```text
群会话 ingest   串行（保序，微秒级）
事件单元组装     串行
worker 执行     并行（受全局 / 每任务上限约束）
上下文提交       串行（单写者）
跨群             并行
```

- 多人同时 @：各自成为独立事件单元，并行处理，不丢消息。
- 队列上限 20，溢出按摘要合并；高优先级（@我、审批）可插队。
- 同群同一时刻只有一个上下文写者；worker 只读快照。
- 禁止“busy 就拒绝”；忙时排队并回执。

### 12.4 回执策略（按实际情况）

- 不回执：能立即回答、群里闲聊、同一 burst 已回执过。
- 回执：任务类、需要查仓库、预计 >5 秒、多人同时 @、需要审批。
- 形式：轻量用表情回应，需要明确承诺用一行文字；私聊可用文字。
- 回执后必须有最终结果或明确转入任务，不能只有回执。
- 对方只是确认或同意：只回“收到”，不分析、不查资料、不追问（`detectReplyDepth`）。
- 对方回复某条消息（`parent_id` / `root_id`）：先带被回复消息与同线程上下文，再解析“哪个/这个”等短指代；owner 群消息默认入库（`context.storeOwnerGroup`）。

### 12.5 提问审批与撤销（已实现）

所有对外的提问都是草稿，不直接发群：

| 动作                   | 行为                                    |
|------------------------|-----------------------------------------|
| `/列表`                | 列出待审批代答，编号 + taskId + 草稿摘要 |
| `/发送`                | 发送最近一条草稿                        |
| `/改写 <新内容>`       | 用我给的内容替换最近一条草稿            |
| `/重写 <要求>`         | 按我的要求重新生成最近一条草稿          |
| `/取消 [编号\|taskId]` | 取消指定草稿；不传参数时取消最近一条     |

- 审批卡展示：已查范围、候选、拟提问内容、`planHash`。
- 我直接在私聊说“不用问了，按 X 做”时，视为把提问转成 `[假设] X` 继续，不发送问题。
- 撤销必须写审计：`question_cancelled`，记录 `jobId`、`messageId`、已查范围。
- 提问被取消后，任务不自动关闭；仍可由我后续补充信息重新激活。

## 13. 验收标准

- [ ] 无 `sourceMessageIds` 的记忆写入被拒绝。
- [ ] `decision / deadline` 未经确认不得 pin。
- [ ] 同一 `chatId + kind + key` 更新产生 supersede，不产生重复。
- [ ] 提炼重跑不产生重复记忆。
- [ ] 评审驳回不写记忆，原文仍保留。
- [ ] 720 天证据可按群/日期检索。
- [ ] 可按群/任务/日期删除证据与记忆。
- [ ] session 删除后，证据与记忆仍可召回。
- [ ] 相关原文不进入群聊，只用于机器人与我。
- [ ] 日志、卡片、prompt 中不出现 App Secret、API Key。
- [ ] 隔 30 秒以上补充的消息能关联到原任务。
- [ ] 已批准/执行中任务不会被自动并入，只提示。
- [ ] 关联合并有审计记录，可回溯 `sourceMessageIds`。
- [ ] 完整事件单元不再回溯历史原文。
- [ ] 不完整事件单元按引用 → 近邻 → 同话题回溯；达到上限只问一个问题。
- [ ] 多人同时 @ 不丢消息，忙时排队而非拒绝。
- [ ] worker 不写群事实；跨任务不串味。
- [ ] 有唯一候选时不提问；提问必须附已查范围与候选。
- [ ] 未检索就提问被拒绝并记审计。
- [ ] 提问草稿可改写、可撤销；撤销后不发送且可回溯。
- [ ] 任务类消息不走代答草稿。
